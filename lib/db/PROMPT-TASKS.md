# Prompt/task storage — prompts/1

Migration0013 is an internal storage foundation. It does not add a public endpoint, an automatic task generator, a running refresher/retention worker or mobile prompts. Later API integration must bind the authenticated account, validate declared context for the displayed subject/scope, enforce Terms on contribution, and expose only a safe mapped response. No writer or account-parameter read is executable by the backend/client roles yet; all ten tables are RLS protected, backend SELECT only. Never grant these impersonation-capable functions directly to mobile roles.

## Registry, task inputs and identity

Nine immutable question definitions record fields/kinds, prerequisite labels, volunteered contexts, schemas, allowed surfaces, priorities and policies. The explicit owner-only task writer deduplicates an active subject/field/scope/question at one generation. Replacements never retarget an old task; closed tasks cannot revive. Stored scope hashes are computed from scope JSON. An automatic generator must validate typed scope, derive actual gaps/conflicts and bind its job lease and generation before calling this writer. Creating a task is not proof that it is eligible.

Reservation checks the requested subject, live generation/lifecycle, usable lead/experience context, and real-clock evidence, independently of a sleeping worker. Unspecified clocks require an active unspecified report. Stale facts require dated due/expired evidence; conflicts require current scoped disagreement and a specific volunteered conflict declaration. Current reported evidence can satisfy a missing-detail invitation without claiming corroboration. Paid fare requires both travelled and paid; unresolved targets additionally require that account's own experience. General route interest and arbitrary viewed/saved context are rejected. New accounts can declare knowledge without reputation/history. Identity and time prerequisites precede dependent questions through deterministic priority, creation time and UUID order.

The invitation binds a conservative hash of transport structure and its parent identities. Generation or another compatible answer alone does not change identity. Structural changes require reconfirmation. This intentionally may request reconfirmation for a parent label/schedule change; future canonical writers must still propagate generations and history, and cross-target actual-journey follow-up requires the later API/association workflow. There is no quiet retargeting.

## Account sessions and feedback

The server owns the current session; no caller-supplied session ID or clock resets it. Account/advisory lock then the shared row guard makes concurrent reservations atomic, including REPEATABLE READ serialization retries. One unsolicited invitation per30-minute activity session and three per rolling24hours. `v2_prompt_touch` records authenticated foreground activity; the API/mobile activity integration is still required. Manual help is budget/preference exempt but still needs relevant task/context. Global opt-out is never silently cleared.

A request receipt records both invitation and no-invitation results. Exact replay never picks a different task. IDs are account bound; changed bodies reject. The invitation ID is the request ID. An expired or redacted receipt is not permission to display: use `v2_prompt_read` and map its status. Unopened invitations expire after15minutes while their budget remains spent. Shown/opened are explicit events, never inferred from reservation. Skip/dismiss suppress across the account until the later of24hours and next midnight in the declared IANA timezone. Unknown suppresses subject/field/scope for30days. Manual help or a newly declared relevant experience bypasses that fact cooldown, preserving global opt-out, account dismissal and caps. Terminal events cannot contradict each other.

An answer is a separate server function, requiring an owned matching active observation and saved intake receipt, with compatible identity. Opening is not answering. It runs in the same transaction as new intake/receipt so rollback removes both the answer metric and submission. Valid late independent evidence remains eligible for answer linkage even after task completion or invitation expiry. The API must check identity before intake and roll back the entire transaction on the final identity conflict, returning a reconfirmation response while preserving the local draft. Linking a previously saved independent report is not a replacement for this submit protocol. No next question automatically opens.

## Erasure, retention and operations

Private account rows cascade on account deletion. Observation erasure removes related task/invitation content and scoped suppressions conservatively; reservation budget rows retain only account/session/time and a redacted retry receipt, so deletion cannot refund another account's nuisance budget. Redacted requests reject replay. No coordinates or background travel histories are stored.

`v2_prompt_prune` is an owner-only atomic maintenance operation. It removes invitation/request cohorts older than90days, expired suppressions and inactive sessions. Before retention deletion, explicit events are counted once by policy/question/outcome only; aggregates contain no account, subject, scope, date bucket or event identifier. Privacy erasure does not create aggregates. Idempotency receipts are available for this bounded90-day retention window, not indefinitely. Retention execution, monitoring and recovery still require WP04/WP09; storage alone does not schedule it. Wrong-target/useful-coverage and timing metrics require the integrated submission/screen instrumentation.

Fresh/repeated and populated upgrade checks, role isolation, adversarial feedback, concurrent device requests and erasure run in disposable PostgreSQL CI. No live migration, role grant or UI delivery follows from this artifact.
