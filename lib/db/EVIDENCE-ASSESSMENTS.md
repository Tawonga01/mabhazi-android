# Evidence assessments

Migration0010 adds deterministic unreviewed assessments for all18 registered fields. Assessments are separate from selected/published field decisions: the existing `v2_field_policy_ready` gate remains in force. No v2 HTTP/mobile feature, reviewer selection interface, running worker or timed departure is enabled by this migration.

## Stored policy and evidence

Five tables hold immutable policy versions, active policy state, assessment history, observation input snapshots and current pointers. Pilot `evidence/1` uses30-day schedule/fare rechecks,90-day place/pattern rechecks,180-day operator rechecks and a seven-day unreviewed disruption cap. Service mode/reported clocks conservatively use the schedule window. Exactly two distinct-account witnesses are required for the pilot; these settings are selected technical policy, not calibrated probabilities. A new policy version and explicit owner activation invalidate current assessments and queue new work. Existing policies cannot be edited.

`v2_assess_field(subject,field,scopeHash,scope,expectedSubject,expectedGeneration,expectedGraph,asOf,requestId)` is owner-only pending authenticated worker/lease integration. It computes the result itself, records evidence snapshots and validates them against the database. A supplied result cannot manufacture corroboration. Exact request retries return receipts without reinstating invalidated effects; changed requests or erased receipts conflict. Subject/input/source revisions and immutable lineage protect concurrent work. All prior observations remain intact. Snapshots contain observation IDs, state/target revisions, source-group footprints, evidence dates and reasons; they do not copy contributor account IDs or private source locators.

## Assessment behavior

Evaluation uses effective observation targets and active evidence, separates field meanings, compares full scope content rather than trusting hashes alone, and canonicalizes decimal amounts without rounding. Scope hash/content disagreement rejects persisted assessment. Missing fare produces no candidate; explicit zero remains a reported amount. Nothing averages prices or clocks.

Within one comparable account/source footprint, keep the latest eligible evidence date, then UUID, recording older repetitions as excluded. Multiple source documents from one account still count as one contributor per candidate. Two witnesses must have distinct active contributor accounts, disjoint known source footprints, complete comparable scope, eligible knowledge basis and current dated ongoing evidence. A compound A+B citation cannot corroborate B. Unknown sources, hearsay, imported/unprovided basis and stale evidence cannot provide witnesses. Contributor counts describe distinct accounts, not independently verified people. Witness ordering is deterministic by date then UUID.

Known comparable current values can produce an open dispute; the result retains candidate values/dates and never silently chooses a winner. Different currencies, passenger/ticket/payment/luggage conditions, fields and service-date scopes remain separate. Sign presence at different places does not conflict. Hearsay/ineligible bases do not open an automatic dispute. Corrections use the existing supersession stream; withdrawal and source changes invalidate the result before recomputation.

Completeness is conservative where stored qualifiers cannot identify a single proposition. A reported lead clock, unresolved operator name, partial stop sequence, approximate coordinate estimate or a pattern-wide pickup answer remains context-needed. Scheduled comparison requires an identified run plus explicit dated applicability and timezone; a calendar UUID alone does not bypass missing qualifiers. Calendar completeness requires a service plan, timezone and explicit dates or bounded weekdays. Multiple pattern pickup locations can coexist; they need finer scope before automatic equality/conflict. Actual-journey pickup/dropoff can be compared within that known journey. Fare completeness requires known passenger/ticket/payment/luggage/time basis and the relevant date/period. These gates preserve facts while leaving alias resolution, precision tolerances, richer endpoint scope and canonical identity integration outstanding.

## Dates and reading

Observed/source dates take precedence over submission/review time. Use the earliest applicable source date across reviewed origin members so a newly uploaded copy cannot refresh an older original. Future/nonfinite evidence dates are excluded even when another older date is available. Inclusive effective periods end independently of the recheck window. Future-effective reports remain stored with a next-change deadline. Unreviewed disruptions expire at the earlier explicit end or seven-day cap; expiration never asserts that service resumed.

Actual departures/arrivals and paid fares are marked historical, with their service date and no claim of ongoing freshness/corroboration. Historical contradiction resolution remains a reviewed workflow; this evaluator does not turn it into a current timetable/price dispute. Unknown dates remain unknown. Recheck deadlines use end of evidence day plus the configured window in the evidence timezone; unknown zones use the conservative UTC+14 expiry boundary and UTC-12 effective-start boundary. JSON instants and receipt hashing use UTC regardless of database session timezone. Service-day seconds, including values beyond24hours, remain unchanged; this is not a departure-instant/DST ambiguity resolver.

The earliest upcoming input change becomes `valid_until` and a durable future assess job. `v2_read_assessment` uses the server's current instant; after expiry, invalidation, retirement or policy change it returns `recheck_required` without the cached support result. The backend cannot supply a historical clock to that function. Raw history is restricted internal data and must never bypass this read boundary in a future public endpoint. No running worker is claimed.

## Invalidation, privacy and remaining integration

New reports advance generations once assessment history exists; source changes, state events and target changes use existing subject-generation propagation. Whole subject assessments invalidate conservatively when required; re-evaluating an old fare keeps its original evidence date when a fresh pickup report arrives. Source-only and account erasure remove copied result/scope/digests and all private input snapshots/IDs in affected assessments. Erased outcomes retain only safe lineage/metadata. Other accounts' original observations survive. Policy changes never resurrect old pointers.

All five tables have RLS and backend SELECT only; PUBLIC/mobile roles and hosted default grants are revoked. Assessment writes, evaluator and historical-clock helpers remain owner-only. No live grants or migration application are performed. Existing field publication constraints stay closed until reviewed selections, historical conflict handling, automatic review-case opening/reopening, rejected-evidence digest handling, all canonical writers, worker leases, question tasks and public projections are connected. Full WP02/WP06 and end-to-end acceptance remain open. The SQL scope/dedup choices are technical refinements to document and calibrate, not a reduction of those requirements.

Validation uses disposable PostgreSQL17: populated0009 upgrade, query mappings, policy/results, copied-source and repeated-account behavior, dates/timezones/expiry, amount/scope separation, revisions/retries, access/erasure and two-connection withdrawal races. Exact passed commits/runs belong in the project manifest; this document alone does not assert a green run.
