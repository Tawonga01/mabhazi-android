# Existing-route endpoint knowledge — route-observations/1

Migration0034 adds two restricted backend facades: read a safe existing-route contribution context, and atomically save endpoint pickup/drop-off observations against that context. It creates no new table, lead, actual journey, timetable or default travel declaration. Initial targets are current community leads visible publicly or owned by the caller. Canonical service targets and intermediate boarding segments need their own typed contract.

Context contains the subject ID, current revision, conservative structural identity hash and explicit city/operator/clock labels. Another compatible answer can advance the revision without changing identity. A structural change, newer-than-current supplied revision, hidden/retired/private foreign target or contributor block refuses a new save. The hash is a concurrency token, not authority or evidence. Context reads do not require accepting contribution Terms; writes require current Terms and an active non-deleting account.

Request observations are one or both of boarding.pickup/alighting.dropoff, once per field. Their named places refer to the selected departure/destination city respectively; scope is empty. Knowledge and observed date remain unknown unless explicitly entered. Only existing caller-owned sources may be cited. UUID/default/source-list canonicalisation and an operation namespace protect the shared account receipt key. Exact historical replay returns its original receipt before current references and never restores a withdrawn report or silently creates another one. Invalid optional evidence rejects the entire transaction.

The contribution, original observations/source links, private receipt and final-generation assessment job commit together. The receipt's optional targetAdvanced flag records a compatible revision advance; saved remains pending, not reviewed/published. No invitation answer is manufactured. Existing account erasure, state/event history, current-time assessment and task invalidation continue to apply. HTTP enforces account headers, authentication, origin/Bearer, strict generated schema plus recursive unknown-member checks, limits and no-store.

Only the backend can invoke these two facades. Hosted roles and PUBLIC cannot; generic constructors and review authority remain restricted. Source checks and exact hosted application are separate stages. This is an API prerequisite for typed forms and later prompt linkage, not a delivered phone feature or complete WP03/WP08/WP09 acceptance.
